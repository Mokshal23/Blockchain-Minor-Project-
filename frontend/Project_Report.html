1. Executive Summary & Problem Statement

Crowdfunding platforms have traditionally relied on centralized database architectures (e.g. KickStarter, GoFundMe). While efficient, centralized platforms present severe vulnerabilities: single points of failure, lack of transparent fund escrow, and susceptibility to insider data tampering by central administrators.

This project designs, implements, and evaluates a Dual-Engine Crowdfunding Architecture to empirically demonstrate the trade-offs between centralized cryptographic hash-chaining (Python SHA-256) and decentralized smart contract execution (Solidity EVM):

  • Python Engine (Donation & Reward Models): Employs custom SHA-256 block ledgering over SQLite for high-speed, zero-gas transactions managed by central admin approvals.
  • Solidity Engine (Equity & Lending Models): Employs Ethereum Smart Contracts on EVM to enforce trustless escrow, weighted contributor milestone voting, and pull-based debt repayments without any central admin key.

2. Dual-Engine Architecture & Design

The platform separates crowdfunding models into two distinct execution pipelines based on risk, regulatory needs, and trust requirements:

3. System Flow & Sequence Diagrams

3.1 Python Engine Execution Flow (Donation / Reward)

  1. Campaign Creation: Startup submits campaign metadata to POST /api/campaigns. Server stores record in SQLite and appends Block #0 to the SHA-256 ledger.
  2. Contribution: User enters amount in inline input box. POST /api/campaigns/:id/contribute appends a block containing {contributor, amount, timestamp, previous_hash}. Reward tier (Bronze/Silver/Gold) is assigned.
  3. Admin Milestone Release: Creator submits milestone proof. Central Admin reviews and triggers POST /api/campaigns/:id/milestones/:mId/approve, releasing funds.

3.2 Solidity Engine Execution Flow (Equity / Lending)

  1. Smart Contract Deployment: User calls createEquityCampaign() or createLendingCampaign() on CrowdfundingFactory.sol. EVM deploys an isolated contract instance and initializes Milestone 0.
  2. On-Chain Contribution: User calls contribute() payable. ETH is locked in contract escrow, and contributor equity share / principal is recorded on-chain.
  3. Weighted Contributor Voting: Contributors vote voteMilestone(id, approve). Voting weight equals investment amount. If YES votes pass 50% threshold, the contract automatically executes owner.call{value: releaseAmount}("").
  4. Lending Pull Repayments: Borrower deposits debt pool via depositRepayment() payable. Lenders pull entitled shares via withdrawRepayment() (Reentrancy-guarded pull pattern).

4. Database & Smart Contract Schemas

4.1 Python SHA-256 Block Structure

class Block: def __init__(self, index, timestamp, data, previous_hash): self.index = index self.timestamp = timestamp self.data = data # JSON: {event, campaign_id, contributor, amount} self.previous_hash = previous_hash self.hash = self.calculate_hash() def calculate_hash(self): block_string = f"{self.index}{self.timestamp}{json.dumps(self.data)}{self.previous_hash}" return hashlib.sha256(block_string.encode()).hexdigest()

5. Centralized Tamper Vulnerability Analysis (Core Project Proof)

The Centralized Hash-Chaining Fallacy:

A common misconception in computer science is that applying SHA-256 hash-chaining to a database makes it immutable. This project empirically disproves this claim for centralized systems.

The Admin Tamper Experiment:

  1. The admin script (POST /api/tamper) secretly accesses the SQLite database.
  2. It modifies a historical block's data payload (inflating a contribution from $100 to $1,000).
  3. Because the central admin holds total database authority, the script re-computes the SHA-256 hash for Block #1 and iteratively recalculates all downstream block hashes in milliseconds.
  4. When the chain validator runs, it compares each block's stored hash against its calculated hash and outputs: Chain Status: VALID (is_valid: true).
Project Conclusion & Thesis Finding:

Cryptographic hash-chaining alone DOES NOT prevent tampering when a single authority controls the database infrastructure. True immutability requires decentralized consensus execution (such as Ethereum Solidity Smart Contracts), where consensus rules prevent any individual from altering state.
